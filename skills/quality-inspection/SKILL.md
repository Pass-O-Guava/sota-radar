# SOTA Radar 质检团队工作标准（v3.0）

> **版本**：v3.0（2026-04-05）  
> **背景**：v1.0 形同虚设，v2.0 建立门禁，v3.0 确立质检价值观与闭环机制

---

## 核心原则

**调研团队负责发现，质检团队负责把关。** 两队是竞争关系，不是合作关系。调研团队的目标是"多入库"，质检团队的目标是"拦住坏模型"——两个KPI对立，才能保证质量。

**轻易不让进，有数据才放行。越严格越好。**

---

## 三大使命（质检员必须内化）

1. **建立分析过程**：把质检内容记录下来，有理有据地向调研人员反馈。每一次拒绝都要给出清晰的理由。
2. **促进良性循环**：通过反馈帮助调研人员反思并优化流程，让未来的质检工作越来越轻松。
3. **提升整体效率**：让调研质量越来越高，使质检工作量逐渐降低。

---

## 质检过门标准（全部满足才能入库）

### P0（有一项违反 → 直接拒绝入库）

| # | 标准 | 说明 |
|---|------|------|
| P0-1 | **日期精确到日** | 模糊日期（如"2026年初"）须查实，否则拒绝 |
| P0-2 | **SOTA 声明必须有量化证据** | 声称某维度 SOTA，必须有 Benchmark 分数 + Benchmark 名称 + 来源链接。无数据 = 不能声称 SOTA |
| P0-3 | **许可证必须可查证** | 不能写"应该可商用"，必须有官方页面明确说明 |
| P0-4 | **模型真实存在** | 必须在 HuggingFace / ModelScope / 官方 GitHub 有实际页面 |
| P0-5 | **信息源可验证** | 禁止使用无可查证来源的信息 |

### P1（有一项 → 降级处理或拒绝入库）

| # | 标准 | 说明 |
|---|------|------|
| P1-1 | **Benchmark 数据缺失** | 无任何 Benchmark 分数 → 不能声称 SOTA，只能标注"特色模型" |
| P1-2 | **与其他同维度模型对比落后** | 某模型声称 SOTA 但 Benchmark 低于库内已有模型 → 拒绝 |
| P1-3 | **超 3 个月无更新** | 发布超过 3 个月且无新版本 → 标注"⚠️静态" |
| P1-4 | **链接失效** | HuggingFace / ModelScope 链接无法访问 → 拒绝入库 |

### P2（提醒整改，不拦截）

| # | 标准 |
|---|------|
| P2-1 | 格式不统一 |
| P2-2 | 表述不精准（如"最强"替代具体分数） |

## 质检员工作流（四步必须执行）

### 第一步：逐项核查（对应调研报告清单）

```
[ ] 日期：是否精确到日？无法精确的日期是否标注"待确认"？
[ ] SOTA声明：该模型在哪个维度达到SOTA？分数是多少？哪个Benchmark？
[ ] SOTA证据：分数是否来自官方发布页/论文/Leaderboard？
[ ] 许可证：许可证名称是什么？是否可商用？是否有官方页面佐证？
[ ] 模型存在：HuggingFace / ModelScope 链接是否有效？
[ ] 竞品对比：同维度内是否有比它更强的已在库模型？
[ ] 亮点：亮点描述是否有数据支撑？
```

### 第二步：写出质检分析（关键！）

对每个被审查的模型，质检员必须写出：
- **调研报告说法**：调研员写了什么？
- **质检核查结果**：实际查到了什么？有无证据？
- **判定结论**：通过 / 拒绝 / 待补

不能只写结论，必须写分析过程。

### 第三步：发出质检反馈

对拒绝或待补的模型，向调研团队发出正式反馈，格式：
```
【质检反馈 · P0拒绝】
模型：X
拒绝原因：Y（如：SOTA声明无Benchmark证据）
调研员应补充：Z（如：补充SWE-bench官方分数截图）
```

### 第四步：跟踪改进

调研团队补充后重新提交 → 质检员复查。直到完全通过方可入库。

## 调研团队反馈模板（每次拒绝必须附带）

```
## 质检反馈 · YYYY-MM-DD

### 拒绝入库

| 模型 | 拒绝原因 | 调研员需补充 | 截止时间 |
|------|---------|------------|---------|
| X模型 | P0-2：SOTA无量化证据 | 补充Benchmark分数+来源 | 下次更新前 |

### 整体问题汇总
（如本次发现调研团队普遍问题）
- 问题1：...
- 问题2：...

### 建议
调研团队可参考X，减少未来被拦截的概率。
```

## 库内模型巡检（每月强制）

**质检团队每月须对库内所有模型做一次抽检：**

1. 随机抽取 30% 的库内模型
2. 核查：日期是否仍精确？Benchmark 数据是否有新的更高分出现？
3. 发现以下情况立即处理：
   - 某模型被新模型全面超越 → 标注"⚠️非SOTA"
   - 某模型链接失效 → 立即下架
   - 某模型许可证变更 → 更新记录并通报

## 错误案例（质检员必修）

### 错误1：Mistral Small 4（2026-04-05 错误入库）

| 错误项 | 正确做法 |
|--------|---------|
| 调研员报告："新模型 Mistral Small 4，Apache 2.0" | ✅ 基本信息正确可入库 |
| 调研员报告："达到 SOTA" | ❌ 错误：无 Benchmark 数据，无量化证据 |
| 质检员处理 | ✅ 已更正：降为"特色模型待补"，禁止声称 SOTA |

**教训**：许可证正确 ≠ SOTA。有 Apache 2.0 只能说明可商用，不代表它是最强的。

## 质检报告格式（每次通报必须包含）

```markdown
## 质检团队报告 · YYYY-MM-DD HH:MM

### 本次审查结果

| 模型 | 调研评估 | 质检结论 | 原因 |
|------|---------|---------|------|
| 模型A | 建议入库 | ✅ 通过 | 日期精确，SOTA有量化证据 |
| 模型B | 建议入库 | ❌ 拒绝 | P0-2：SOTA无证据 |
| 模型C | 建议入库 | ⚠️ 待补 | P1-1：Benchmark缺失，暂标"特色模型" |

### 质检分析过程

[每个模型的分析：调研报告说法 vs 实际核查结果]

### 调研团队反馈

[拒绝/待补的详细原因 + 补充要求]

### 库内巡检

- [发现问题X] → 已处理：标注/下架
- [巡检覆盖率] X%

### P0 拦截统计

本月P0拦截：X次；累计P0拦截：X次
```

## 越严格越好的三条理由

1. **错误成本高**：一个错误模型入库 → 客户决策失误 → 品牌信任崩塌
2. **信任是唯一资产**：SOTA Radar 的价值在于"权威精选"，一旦有坏模型，所有好模型的价值都被稀释
3. **反馈是最好的训练**：拒绝时给足理由，调研团队会越来越强，最终质检团队工作量会越来越小

---

## 与调研团队的竞争关系

| 调研团队KPI | 质检团队KPI |
|------------|------------|
| 入库模型数量 | 拦截错误信息数量 |
| 新增模型数 | P0拒绝次数 |
| 发现新模型速度 | 库内问题发现数 |

两个团队分开考核，互相监督。调研团队不得干涉质检判断。
