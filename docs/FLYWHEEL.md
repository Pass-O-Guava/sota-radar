# 🔄 数据飞轮 & 知识进化机制

> **设计者**：@pm | **版本**：v1.0 | **日期**：2026-04-05

---

## 一、为什么需要飞轮

SOTA 模型领域变化极快（2026年已有 GPT-5、GLM-5、Kimi K2.5 等密集发布）。传统"一次性建库"模式会在两周内过时。必须建立**自我更新**的机制。

---

## 二、双飞轮架构

```
  ┌─────────────────────────────────────────────────────────┐
  │                    知识飞轮（内容层）                      │
  │                                                          │
  │  HuggingFace/ModelScope/HuggingFace Spaces               │
  │         ↓ 每日两次抓取                                    │
  │  @vlm-researcher · @text-researcher · @reviewer         │
  │         ↓ 产出模型卡                                      │
  │  models/ 目录更新（JSON/Markdown）                       │
  │         ↓                                                 │
  │  OVERVIEW.md 自动汇总 → README.md 更新                    │
  │         ↓                                                 │
  │  GitHub 推送 → SOTA Radar 页面刷新                       │
  │         ↓                                                 │
  │  飞书推送报告 → 用户接收最新洞察                          │
  │         ↓                                                 │
  └────────────── ↺ 循环（次日重复） ─────────────────────────┘

  ┌─────────────────────────────────────────────────────────┐
  │                    质量飞轮（机制层）                      │
  │                                                          │
  │  调研员产出 → @reviewer 质检拦截（P0/P1/P2）            │
  │         ↓                                                 │
  │  发现问题 → 反馈调研员整改 → 重新提交                     │
  │         ↓                                                 │
  │  质检统计 → 周报 → 月度复盘                               │
  │         ↓                                                 │
  │  典型问题 → 沉淀到 SOP / 检查清单                         │
  │         ↓                                                 │
  │  团队能力提升 → 更高一次通过率 → 更快迭代                 │
  └────────────── ↺ 循环（持续进化） ─────────────────────────┘
```

## 三、每日运转流程（每日两次）

### 调度时间（北京时间）
- **早间版**：09:00 — 针对亚洲发布动态（阿里巴巴、智谱AI、Moonshot 等）
- **晚间版**：21:00 — 针对美国发布动态（OpenAI、Google、Anthropic 等）

### 执行流程（每次）

```
Cron 触发
  ↓
检查各模型发布平台（HuggingFace Trending / ModelScope 新增 / 官方博客）
  ↓
若发现新模型（发布日期 ≥ 上次扫描日期 - 7天）：
  → @coordinator 调度专项调研员
  → 调研员产出模型卡
  → @reviewer 质检拦截
  → 更新 OVERVIEW.md
  → GitHub push
  → 飞书推送增量报告
  ↓
若未发现新模型：
  → 更新"最后扫描时间"
  → 仅更新 scan-log.md（轻量）
  ↓
完成，报告推送飞书
```

## 四、知识沉淀规则

每次更新必须同时完成三项沉淀：

| # | 类型 | 路径 | 说明 |
|---|------|------|------|
| 1 | 模型知识更新 | `docs/OVERVIEW.md` | 横向对比更新 |
| 2 | 调研方法改进 | `team/skills/` | 从错误中提炼 SOP |
| 3 | 行业洞察 | `docs/INSIGHTS.md` | 本次更新的趋势判断 |

---

## 五、质量拦截机制

| 等级 | 触发条件 | 处理方式 |
|------|---------|---------|
| **P0** | 日期造假 / SOTA 无证据 / 自相矛盾 | 直接拒绝，计入调研员 P0 错误 |
| **P1** | 信息不完整 / 链接失效 / 许可证错误 | 打回整改，整改后重新提交 |
| **P2** | 格式问题 / 表述不精准 / 过期信息 | 提示修正 |

---

## 六、竞对 KPI 对立机制

| 团队 | KPI | 方向 |
|------|------|------|
| 调研团队 | 通过质检的模型数量 | 越多越好 |
| 质检团队 | 拦截的错误数量 | 越多越好 |

两方对立，@pm 最终裁判，形成正向淘汰压力。

---

## 七、触发条件

| 事件 | 动作 |
|------|------|
| 每日上午 09:00 UTC+8 | 启动亚洲区模型扫描 |
| 每日晚间 21:00 UTC+8 | 启动欧美区模型扫描 |
| 发现重大模型发布 | 立即触发专项调研，不等定时 |
| 单一模型突破 SOTA | 触发实时更新 + 推送报告 |

---

## 八、GitHub 自动同步

- 每次更新自动 push 到 `Pass-O-Guava/sota-radar`
- `README.md` 实时反映最新状态
- 重大版本更新打 tag（v0.4、v0.5...）
- Scan log: `docs/scan-log.md`
